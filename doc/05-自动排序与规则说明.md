# 自动排序与规则说明

这份文档说明 RimCrow 的自动排序、规则来源和问题提示。它适合已经完成扫描，并准备整理加载顺序的用户。

先记住一句话：自动排序能帮你得到更合理的基础顺序，但不能保证所有 Mod 组合都一定正确。

## 自动排序做了什么

自动排序会读取当前启用列表、Mod 依赖信息和各类规则，然后重新排列 Mod 顺序。

它主要处理：

- 前置依赖应排在被依赖 Mod 前面。
- 明确要求“加载在某个 Mod 之后 / 之前”的规则。
- 置顶、置底和权重倾向。
- 语言包、兼容补丁、性能优化等常见顺序建议。

排序完成后，仍建议查看红色错误和黄色警告。

## 排序原理简化理解

可以把自动排序理解成三步：

1. 先看必须满足的关系：例如前置依赖、必须在谁前面、必须在谁后面。
2. 再看大致位置倾向：例如置顶、置底、权重靠前或靠后。
3. 最后做局部整理：在不破坏前面规则的前提下，让相关 Mod 尽量靠近。

也就是说，自动排序不是简单按名称或订阅时间排列。它会先保证重要关系，再考虑“看起来更顺”的位置。

举个简单例子：

```text
A 是框架，B 依赖 A，C 是 B 的语言包
```

排序时通常会让 A 在 B 前面。如果开启语言包贴靠，C 会尽量跟在 B 附近，而不是被单独甩到很远的位置。

如果某些规则互相打架，RimCrow 会尽量保留更重要、更可信的规则，并把无法同时满足的规则提示出来。

## 自动排序不能保证什么

自动排序不能替你判断所有 Mod 的真实兼容性。

这些情况仍需要人工确认：

- Mod 作者没有写完整依赖信息。
- 社区规则还没有覆盖这个 Mod。
- 两个 Mod 的兼容关系只在说明页里提到。
- 同一 PackageId 有多个来源副本。
- 你使用的是整合包、测试版或旧版 Mod。

## 规则来源

RimCrow 会综合多种规则来源。不同来源可以共同参与排序和问题检测。

### 原生规则

来自 Mod 自己的 About.xml、依赖声明和基础信息。

这类规则通常最可靠，因为它来自 Mod 文件本身。但有些 Mod 写得不完整，仍可能需要其它规则补充。

### 用户规则

由你自己为某个 Mod 写的规则。适合长期固定自己的使用习惯。

常见用途：

- 指定某个 Mod 必须在另一个 Mod 前后。
- 给某个 Mod 设置权重。
- 忽略你确认无影响的提示。
- 修正社区规则没有覆盖的组合。

### 社区规则

来自社区维护的排序规则库。它可以补充大量常见 Mod 的排序建议。

注意：

- 社区规则是建议，不代表对所有环境都绝对正确。
- 规则库需要更新，旧缓存可能缺少新 Mod。
- 如果规则和你的实际测试冲突，可以用用户规则覆盖或调整。

### 创意工坊规则

来自创意工坊离线数据库和相关依赖信息。它可以帮助识别工坊项目之间的关系。

如果开启“作为强依赖”，工坊规则会更严格地参与依赖判断。普通用户不确定时，先保持默认。

### 动态规则

动态规则更像自动化条件：

```text
如果 Mod 满足某些条件 -> 执行某种排序动作
```

适合批量处理有共同特征的 Mod，例如按标签、类型、作者或名称规则整体前移、后移、置顶或置底。

## 生效优先级

规则中心里可以调整规则来源优先级。优先级会影响规则冲突时更相信哪一类来源。

简单理解：

- 越靠上，优先级越高。
- 用户规则通常适合放在较高位置，用来表达你自己的最终选择。
- 不确定时不要频繁调整全局优先级，先处理具体 Mod 的问题更稳。

## 权重怎么理解

权重用于表达排序倾向。数值越小，越靠前；数值越大，越靠后。

常见理解：

- 置顶：强制靠前。
- 置底：强制靠后。
- 权重设定：直接给一个目标区间。
- 权重偏移：在原本位置倾向上前移或后移。

权重适合表达“这一类 Mod 大概应该靠前或靠后”，不适合替代明确依赖关系。

简单说：

- 依赖和前后规则更像“必须这样排”。
- 权重更像“没有硬性冲突时，尽量往这里排”。
- 置顶、置底比普通权重更强，适合少数确实需要固定在两端的 Mod。

不要给太多 Mod 随手设置置顶或置底。两端规则太多时，排序结果反而更难理解。

## 贴靠行为

贴靠是自动排序后的局部整理。它的目的不是改变规则，而是让有关联的 Mod 看起来更集中。

相关开关在设置中控制。关闭时，排序仍会按依赖、规则和权重处理，只是不会额外做贴靠整理。

### 语言包贴紧前置

开启后，语言包会尽量跟在它对应的主 Mod 或最后一个已启用前置后面。

这样做的效果是：

- 语言包更容易和主 Mod 一起检查。
- 不容易出现语言包全部堆在列表底部，离主 Mod 很远的情况。
- 语言包较多时，列表会更容易看懂。

注意：

- 如果找不到对应主 Mod，语言包会保持原本的默认靠后位置。
- 如果贴过去会破坏依赖或其它排序规则，RimCrow 不会强行移动。
- 如果语言包归属识别不准，可以手动调整顺序，或写用户规则指定关系。

### 普通 Mod 贴紧依赖

开启后，普通 Mod 会尽量靠近它最后一个已启用的直接依赖。

这样做的效果是：

- 同一系列或有关联的 Mod 更容易聚在一起。
- 列表不会只按大范围权重分散排列。
- 检查“这个 Mod 依赖谁”时更直观。

注意：

- 这个贴靠主要在相同权重范围内移动，不会随便跨过重要分区。
- 置顶、置底、语言包等特殊位置不会被普通贴靠强行打乱。
- 如果前后规则不允许靠近，RimCrow 会保留更安全的顺序。

### 贴靠不是强制相邻

贴靠的意思是“尽量靠近”，不是“必须挨着”。

如果中间还有必须插入的依赖、补丁、框架或规则要求，相关 Mod 之间仍可能隔着其它 Mod。这通常不是排序失败，而是为了避免破坏更重要的加载关系。

## 冲突规则怎么处理

有时不同规则会形成闭环，导致任何顺序都不可能完全满足。

例如：

```text
A 必须在 B 前面
B 必须在 C 前面
C 又必须在 A 前面
```

这种情况下，不管怎么排，至少都会违反其中一条规则。

RimCrow 会先给出一个当前能满足最多规则的顺序，然后提示“排序规则冲突”。在冲突视图中：

- 红色规则线表示本次被忽略的规则。
- 其它规则线表示当前排序仍然保留的规则。
- 右侧会显示规则来源，方便判断该调哪一条。

处理建议：

- 如果是用户规则写错了，直接修改或删除用户规则。
- 如果是动态规则范围太宽，收窄条件或暂时关闭这条动态规则。
- 如果是社区规则、工坊规则与你的环境不符，可以关闭对应 Mod 的该来源规则。
- 如果是原生规则，它来自 Mod 文件本身，不能单独禁用，只能调整其它规则或手动处理。

看到冲突提示不代表自动排序完全失败。它表示 RimCrow 已经排出了一个可用的当前结果，但有至少一条规则无法同时满足，建议你确认一下。

## 问题提示怎么处理

### 缺少依赖

表示当前启用列表缺少某个必要或建议前置。

处理方式：

- 如果你确实需要这个 Mod，先补齐依赖。
- 如果这是可选依赖，确认无影响后可忽略。
- 如果缺失项来自导入列表，尝试补订阅或补下载。

### 排序错误

表示当前顺序不满足依赖或规则要求。

处理方式：

- 先尝试自动排序。
- 如果仍不对，手动拖拽调整。
- 长期需要固定时，写用户规则。

### 不兼容

表示规则认为两个 Mod 不能同时使用，或需要你确认兼容补丁。

处理方式：

- 先查看 Mod 说明或工坊页面。
- 只保留其中一个。
- 安装兼容补丁。
- 你确认无影响时，再选择忽略或写规则。

### 语言包提示

语言包通常需要跟随它对应的主 Mod。RimCrow 会尽量识别语言包归属，但有些语言包信息不完整。

处理方式：

- 确认主 Mod 是否已启用。
- 让语言包排在合适位置。
- 如果识别错了，可以在规则里手动指定。

## 推荐工作流

### 普通排序

1. 扫描。
2. 启用需要的 Mod。
3. 点击自动排序。
4. 查看红色错误。
5. 手动处理无法自动解决的问题。
6. 保存。

### 创建自己的规则

适合反复遇到同一个排序问题时使用。

1. 找到相关 Mod。
2. 打开规则编辑。
3. 添加加载前后、权重或忽略规则。
4. 保存规则。
5. 重新自动排序并检查结果。

不要为了临时测试写太多规则。一次性的顺序调整，直接拖拽更简单。

### 使用动态规则

适合你已经给 Mod 做了标签、类型或分组整理，并希望批量影响排序。

例如：

- 带“语言包”标签的 Mod 靠后。
- 某个作者的一系列框架靠前。
- 某类视觉替换靠后。

动态规则影响范围更大，保存前建议先确认筛选条件没有写得太宽。

## 常见问题

### 自动排序是不是越多规则越好？

不是。规则太多、来源冲突或范围过宽，都可能让结果难以理解。优先保留真正有用、能解释清楚的规则。

### 社区规则和用户规则冲突怎么办？

如果你明确知道自己的环境需要某种顺序，用用户规则表达。用户规则更适合承载你的最终选择。

### 修改规则后为什么列表没变化？

通常需要重新自动排序。规则保存后只是改变判定依据，不一定立即重排当前列表。

### 忽略警告安全吗？

只有在你理解原因并确认对当前环境无影响时才忽略。不要用忽略来掩盖红色错误。

## 注意事项

- 自动排序前建议先扫描，保证 Mod 信息是最新的。
- 排序后必须保存才会写入加载顺序。
- 长期有效的判断写成用户规则，临时测试直接手动拖拽。
- 动态规则范围要收窄，避免误伤大量 Mod。
